# Viator Specifications V2

This document is generated by AI, manually reviewed by author lamadaemon

Viator is a modern C and C++ build and package system configured with Luau.
It is intended to replace the environment-dependent conventions common in the
C and C++ ecosystem with explicit dependencies, predictable build semantics,
and reproducible artifacts.

Viator combines four ideas:

- Gradle-like dependency management using JSON package metadata.
- A Luau build language made from composable actions and pipelines.
- A concurrent Rust job engine with typed artifact flow.
- An isolated package repository whose products affect the host only after an
  explicit mount operation.

Standard libraries are dependencies. A project may request virtual facilities
such as a C library, C++ standard library, compiler runtime, loader, or embedded
board support. The selected toolchain supplies default providers, but projects
may request another compatible provider explicitly. A project that requests no
standard-library facilities is naturally freestanding; it does not need a
special `none` operating-system target.

Viator does not use an OS triplet as its primary compatibility model. Package
variants describe machine requirements such as architecture and required CPU
features. Runtime and environment assumptions are represented by resolved
dependencies. Viator validates the combined machine, toolchain, ABI, and
runtime requirements before building or consuming an artifact.

Build descriptions contain pipelines of actions. An action is a job factory,
not a unit of execution. For example, `CLang:CompileAll` can produce one compile
job per source file, allowing the Rust scheduler to execute independent jobs
concurrently. Jobs exchange immutable, typed artifact references through an
append-only context, so users do not have to name every object file or other
intermediate result.

Targets and pipelines share one internal representation. A target is simply a
named pipeline exposed through the project and CLI. Pipelines compose through
`CallPipeline` rather than through a separate target dependency mechanism.

Locally published packages remain isolated in the Viator repository. They do
not modify `PATH`, loader configuration, system directories, or the current
environment. `viator mount` creates an explicit activation view for selected
commands and their runtime dependency closures. Mounting should prefer private
library paths and launch wrappers over modifying published binaries.

LLVM-based toolchains are the default and reference implementation. Other
toolchains, including GNU-based toolchains, may implement the same semantic
language support contract. The core supports x64, but intentionally does not
support 32-bit x86. An external plugin may provide 32-bit x86 support without
adding architecture-specific code to the Rust core.
